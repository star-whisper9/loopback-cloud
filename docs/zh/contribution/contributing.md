这是一份面向所有贡献者的规范性说明。提交代码、文档、翻译、资源或问题反馈前，请先阅读本页；文档的 Frontmatter 和 Markdown 扩展语法请继续参考[文档格式与语法参考](guide)。

## 项目原则

环回云是一个社区协作项目。我们更看重真实、可复现、可审阅的内容，而不是提交数量或文字数量。

贡献内容应满足以下原则：

- 有明确的使用场景和目标读者
- 尽量提供验证环境、版本号、前置条件和预期结果
- 不隐藏风险，不把未经验证的猜测写成确定结论
- 不提交秘密、隐私数据、受限制的第三方内容或无法确认来源的材料
- 保持变更范围清晰，避免在一个 Pull Request 中混入无关重构

## 可以贡献什么

欢迎以下类型的贡献：

- 修复页面、路由、静态资源和交互问题
- 改进可访问性、移动端布局和错误提示
- 增加或完善家里云相关的真实实践文档
- 修正文档中的命令、版本、链接、事实和翻译
- 补充测试、构建检查和开发者工具
- 提交可复现的问题报告和改进建议

## 不接受什么

以下内容不会被合并，或需要先补充充分证明：

- 未经验证的整段转载、营销稿或与家里云无关的推广
- 泄露密码、令牌、私钥、Cookie、个人信息或内网拓扑的内容
- 将大段 AI 生成内容直接作为最终稿提交，且没有人工核对
- 缺少风险说明的磁盘、网络、固件、权限和数据破坏操作
- 绕过安全控制、侵犯他人权益或用于违法用途的内容
- 仅为了个人风格而进行的大范围格式化或无关重命名

## 贡献流程

### 1. 提交前确认

小型拼写修正可以直接创建分支。涉及新功能、目录调整、许可证、构建配置或大量文档时，建议先创建 Issue 说明目标和方案，避免重复工作。

提交前先确认：

- 是否已经存在相同问题或文章
- 变更属于代码、文档、翻译还是第三方资源
- 是否拥有提交内容的版权或再发布权限
- 是否需要同步更新中文基准文档、英文译文或测试

### 2. 创建分支

从最新的 `main` 创建短期分支。推荐使用以下前缀：

| 前缀     | 用途             |
| -------- | ---------------- |
| `docs/`  | 文档、示例和翻译 |
| `fix/`   | 错误修复         |
| `feat/`  | 新功能           |
| `test/`  | 测试和验证       |
| `chore/` | 构建、依赖和维护 |

一个分支应围绕一个目标，完成后尽快提交 Pull Request。

### 3. 修改内容

文档修改应遵守以下路径规则：

- 中文基准文档放在 `docs/zh/`。
- 英文译文放在 `docs/en/`，并与中文保持相同的文章路径。
- 分类目录使用 `_category.md` 设置标题和排序。
- 文章文件名使用小写 kebab-case，例如 `network-backup.md`。
- 分类目录内不要使用 `index.md` 作为文章名；构建脚本会忽略它。
- 文档元数据必须包含 `title`；时间字段建议明确写出时区。
- 正文从 `##` 开始，危险操作使用 `:::warning`，代码块标注语言。

代码修改应遵守以下规则：

- 优先修复实际问题，不为简单逻辑增加不必要的抽象。
- 浏览器专属 API 放在客户端代码路径中，不要让静态构建依赖运行时服务器。
- 修改路由、基础路径或静态资源时，同时检查首页、控制台和文档深层 URL。
- 不要删除或替换根目录 `components/` 中的上游许可证、来源说明或版权信息。
- 如果复制或修改第三方 UI 组件，应在 Pull Request 中说明来源、改动范围和适用许可证。

### 4. 本地验证

文档或代码变更至少运行：

```bash
npm ci
npm run build:docs
npm run typecheck
npm test
npm run build
```

验证重点：

- 构建没有 Frontmatter、类型或打包错误
- 首页、`/console` 和 `/docs/...` 能够直接打开
- 生产构建没有错误的根绝对资源路径
- 文档目录顺序、标题锚点、代码高亮和语言回退正常
- 危险操作带有清晰的警告、影响范围和恢复建议

`app/docs/.generated/docs.ts` 由 `scripts/build-docs.ts` 生成。不要手动编辑它；修改文档后运行 `npm run build:docs`，检查生成差异是否只包含本次文档变更。

### 5. 提交 Pull Request

Pull Request 标题应直接说明目的，例如：

- `[docs] 增加 ZFS 快照备份指南`
- `[fix] 修复文档深层链接加载失败`
- `[feat] 增加实例状态筛选`

描述中请包含：

- 变更目的和主要内容
- 影响的页面、文档路径或组件
- 使用过的系统和软件版本（如果适用）
- 已执行的验证命令及结果
- 已知限制、兼容性问题或后续工作

### 6. 审阅与合并

审阅者会重点检查事实准确性、可复现性、风险提示、许可证边界、移动端表现和构建结果。贡献者应直接修正问题，不要通过删除测试、隐藏警告或放宽校验来绕过审阅。

只有在检查通过、关键意见处理完毕且变更范围清晰时，Pull Request 才适合合并。合并后请删除临时分支。

## 翻译规范

中文内容是事实和结构基准，英文翻译不是每篇文章都必须同步完成。翻译时：

- 保持文章路径、命令、配置项、版本号和风险等级一致
- 不要为了语言习惯改变技术结论或省略限制条件
- 使用 `translator.type` 标记 `machine`、`llm`、`human` 或 `mix`
- AI 翻译必须人工核对命令、路径、选项、错误信息和警告
- 缺少英文文章时，站点会显示中文回退内容并提示读者

## 许可证与版权

- 项目自有代码（根目录 `components/` 中的上游 UI 组件除外）使用 GPL-3.0-or-later。
- `README.md`、`docs/` 和项目自有文档素材使用 CC BY-SA 4.0。
- 根目录 `components/` 中的 shadcn/ui、Aceternity UI 等上游组件不适用项目的统一许可证声明，必须保留并遵守各自来源的许可证。
- 第三方依赖、字体、图标、图片和示例内容不因提交到本项目而自动转为项目许可证。
- 贡献者保留原创贡献的版权；提交贡献表示你有权提交，并同意按照对应内容类型的许可证发布。

项目目前不要求单独签署 CLA。如果你不能确认自己拥有某段代码、文字、图片或翻译的再发布权，请先不要提交，并在 Issue 中说明来源和授权情况。

## 问题反馈

有效的问题报告应尽量包含复现步骤、期望结果、实际结果、浏览器和系统版本、相关 URL，以及不包含敏感信息的控制台错误。安全问题不要公开发布，请通过私下渠道联系维护者。

感谢每一位让环回云更真实、更可复现、更容易维护的贡献者。
